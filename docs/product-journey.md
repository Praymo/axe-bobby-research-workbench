# Product journey: 从“选股分数”到“可复核的决定”

## 起点：信息很多，但决定没有被保存

最初的问题并不是“没有一个模型”。研究材料、行情、新闻和聊天里都有信息，真正容易丢掉的是它们之间的关系：当时看到什么、采用了什么假设、哪些条件没有满足、后来为什么继续看或停止看。

如果最后只留下一个 0–100 分，下一次复盘很难知道分数代表什么。Axe Bobby 因此从一个可解释的六维研究评分开始，但很快发现研究质量、入场时点和风险边界不能用同一层解决。

## 观察到的问题

### 研究分容易被误读成交易信号

基本面和行业逻辑变化较慢，价格位置和市场风险变化很快。把它们加成一个分数，会把“值得长期研究”和“今天适合新建仓位”混在一起。

### 数据缺口很容易被漂亮的页面遮住

缺字段、错误单位和过期行情不应该被填成一个中性分。否则页面越完整，使用者越容易忘记哪些地方其实不知道。

### 自动化容易跨过确认边界

Agent 可以捕捉、整理和提醒，但确认一条计划不等于下单。网页、Telegram 和 Codex 如果各自维护状态，重复通知和互相覆盖也会让责任边界变模糊。

## 产品判断

这些观察最后变成了几条实现约束：

1. 研究分、入场分和风险闸门分层；每层都有自己的输入和失败状态。
2. 每个因子保留来源、数据截止日、原始值和适用性；不适用就不显示，缺失就阻断需要它的判断。
3. 每个建议带有 `advice_id`、证伪价、目标、盈亏比和 `requires_confirmation`；它是待复核对象，不是订单。
4. 过期快照冻结新的计划确认，但仍允许查看历史结果和做否决、记录与复盘。
5. 影子模型和主题 Playbook 必须经过样本外验证、定义冻结和影子运行，才能讨论是否进入正式评分；当前公开版本不提供自动晋级。

## 从功能到数据层

工作台的五层数据结构不是为了增加名词，而是为了回答“这句话从哪里来”：

| 层 | 记录什么 | 一个决定 |
| --- | --- | --- |
| 事实层 | 行情、公司资料、新闻、来源与日期 | 这条输入是否存在、是否新鲜 |
| 证据层 | 六维因子、原始分、警告与缺口 | 研究判断由哪些证据支持 |
| 决策层 | 权重、关注分、位置分、计划和版本 | 为什么进入候选、哪里失效 |
| 事件层 | Codex、Telegram、网页写入的统一事件 | 什么时候捕捉、确认、否决或复盘 |
| 文件层 | 研究附件与元数据 | 哪个文件属于哪个标的和研究记录 |

快照由 Python 主流水线生成，Web 只负责读取和记录决定。这样同一份历史快照可以重放，页面也不会在“刷新”时悄悄重新计算一套不同的结果。

## 当前版本最重要的失败路径

- 市场状态 `risk_off` 或数据过期时，不出现“等待确认”的新开仓计划。
- 研究分很高但没有止损、盈亏比不足或支撑失效时，进入 `BLOCKED` 或 `MONITOR`。
- 影子模型即使通过部分门槛，也保留 `SHADOW_ONLY` 和 `NOT_ELIGIBLE_FOR_AUTOMATIC_PROMOTION`。
- 未登录时，用户事件、研究笔记和文件 API 返回空结果；不会把公开快照误当成某个真实账户的数据。
- 公开快照删除原始 Agent 文本，只展示事件契约和产品边界。

这些路径看起来不像“成功演示”，但它们恰好是我希望投研工具认真处理的部分：系统应该能明确说“不知道”“现在不能做”和“这只是实验”。

## 还没有验证的事

公开版本可以验证页面、状态和数据边界，不能证明收益、预测稳定性、真实用户效率或模型长期有效。影子模型中的样本外数字也只是随附快照的研究结果，不是实盘业绩。

下一轮验证应该先围绕错误做：哪些候选被过期数据挡住、哪些研究在入场层被否决、哪些提醒重复、哪些复盘字段真正帮助下一次判断。只有这些问题有记录，才值得扩大自动化范围。

## 为什么把它公开

这是我自己做的工作台，但我不想把技术只用来形成个人的信息差。公开它，一方面是让别人能检查我的假设和边界，另一方面也是希望同学可以直接拿去改、复用或指出问题。一个人借助工具完成项目，并不意味着结果只能服务于自己；把流程写清楚、把失败状态留下来，本身就是产品的一部分。
